# MicroViber Track B — Design Spec

> Status: design approved 2026-08-27 · Branch: `feature/microviber` (Harness)
> Scope: the three Track B feature stories from [production-readiness.md](../microviber/production-readiness.md) §5 — PWA installability, embedded dev-server browser, UX/UI polish — plus two requirements (transcript link handling, `AskUserQuestion` support) added during this spec's own review cycle. Companion to [spec.md](../microviber/spec.md) (Track A product design, shipped) and `microviber/docs/architecture-spec.md` / `microviber/docs/functional-spec.md` (the in-repo specs this amends).
> This spec documents several explicit deviations from the constraints locked in `production-readiness.md` §5 — see §9.

---

## 1. Overview

Track A shipped the takeover-via-resume write path. Track B adds five feature areas. Four are UI-shell-facing or daemon-config-facing, touching neither the Claude Code integration contract (§2 of `architecture-spec.md`) nor the adapter quarantine; the fifth (Feature 5) is the exception — it requires a real change to Track A's shipped session-state derivation, flagged explicitly where it's discussed:

1. **PWA installability** — real manifest, icons, in-app install button. Android/Chrome only.
2. **Embedded dev-server browser** — a same-origin reverse-proxy pane so the phone can view a session's local dev server, with best-effort port resolution. Generalized into a **Web pane** that also serves local files (§5), sharing one auth and iframe-isolation mechanism.
3. **UX/UI polish** — a dedicated title bar, and a session picker restructured around a short "Recent" list with folder browsing as a secondary path.
4. **Link handling in agent output** — transcript links open either in the Web pane (local) or the phone's own browser (external).
5. **`AskUserQuestion` support** — MicroViber currently has no way to see or answer a Claude Code `AskUserQuestion` tool call, which also currently blocks *takeover itself* for up to an hour (§6) — not just a missing UI, a real state-derivation bug.

All UI-facing features share one mechanism worth calling out up front: **a single dropdown-caret button style** (rounded-square, bordered, SVG chevron, amber when open) used identically for both the session picker (attached to the session header) and the Web pane's address bar — one consistent interaction affordance across the app, not two.

## 2. Feature 1 — PWA installability

### Manifest

Replaces `pwa/public/manifest.webmanifest`'s current `icons: []` stub:

```json
{
  "name": "MicroViber",
  "short_name": "MicroViber",
  "description": "Mirror and drive your Claude Code sessions from your phone.",
  "start_url": "/",
  "scope": "/",
  "display": "standalone",
  "background_color": "#09090b",
  "theme_color": "#09090b",
  "orientation": "portrait",
  "icons": [
    { "src": "/icons/icon-192.png", "sizes": "192x192", "type": "image/png", "purpose": "any maskable" },
    { "src": "/icons/icon-512.png", "sizes": "512x512", "type": "image/png", "purpose": "any maskable" }
  ]
}
```

### Icon deliverables (source-provided by the user, not generated by this story)

| File | Location | Size | Notes |
|---|---|---|---|
| `icon-192.png` | `pwa/public/icons/` | 192×192 | `any maskable` purpose. Content centered in the inner 80% safe zone (≥10% padding each side); background fully opaque, filling every edge — no transparency, since Android crops the full square to its own shape. |
| `icon-512.png` | `pwa/public/icons/` | 512×512 | Same art, scaled up. Used for splash screens / app switchers. |
| `apple-touch-icon.png` | `pwa/public/` | 180×180 | Referenced via `<link rel="apple-touch-icon">` in `index.html` (iOS ignores the manifest for this). Opaque background. Included so it isn't broken if a user manually adds to home screen — no iOS-specific detection or fallback UI is built (see §9). |
| `favicon.png` | `pwa/public/` | 32×32 | Browser tab icon. Not part of installability criteria; included for polish. |

Suggested background: the app's existing `#09090b` (zinc-950), so the icon blends if a platform doesn't crop it. All PNG, sRGB.

### Install button

- Lives in the new title bar (§4), right-aligned.
- Rendered only when: (a) the `beforeinstallprompt` event has fired and been captured, and (b) `window.matchMedia('(display-mode: standalone)').matches` is `false`. Both conditions must hold — no button on iOS Safari (event never fires there) and no button once already installed.
- Tapping it calls `.prompt()` on the captured `beforeinstallprompt` event.

### Service worker

`pwa/public/sw.js` is unchanged — its existing push-notification-only registration (no `fetch` handler) already satisfies current Chrome/Android installability criteria once the manifest and icons above are in place. No new caching strategy is in scope.

## 3. Feature 2 — Embedded dev-server browser

### Port resolution

For a session's folder (its `cwd`), the daemon resolves a dev-server port through three tiers, in this precedence — **first match wins**:

1. **Project `.env`** — a `PORT=<value>` line at the folder's root, read as a plain text-line match (`/^PORT=(\d+)$/m`). The file is never imported, required, or executed — only its raw text is scanned.
2. **`microviber/devports.json`** — daemon-owned, keyed by the folder's **full absolute path** (not basename, to avoid collisions between differently-located folders that happen to share a name):
   ```json
   {
     "/Users/you/Harness-2/studio": { "port": 9005, "framework": "next", "startCommand": "npm run dev" },
     "/Users/you/Harness-2/audio-producer": { "port": 9008 }
   }
   ```
   `framework` and `startCommand` are optional metadata, not currently used by the proxy itself — carried for a future UI affordance (e.g. "dev server not running, here's the command") that is out of scope for this story.
3. **Static config scan** — a non-executing regex/text scan of `vite.config.*`, `angular.json`, `webpack.config.*`, and `package.json`'s `scripts` entries, looking for a `port:` field or `--port <n>` flag. Lowest-confidence tier; used only when neither of the above resolves anything.

If no tier resolves a port, the folder has no dev-server pane — the Web pane for its sessions shows an empty state ("nothing configured"), and mirror/takeover for the session itself are unaffected.

**Not built in this story:** a fourth "runtime verification" tier (inspecting actually-listening loopback sockets to confirm/override the above) was considered and explicitly dropped from scope — see §9.

### The Web pane's two content sources

The pane originally scoped for dev-server browsing is generalized to a **Web pane** with two content sources sharing one auth mechanism (below) and one iframe: a proxied dev server, and (added for Feature 4, §5) a served local file. Both live under one route namespace, `/api/webpane/*`.

### Proxy route (dev server)

`/api/webpane/devserver/:port/*` (all standard HTTP methods, not just GET/POST — the proxy is generic) on the daemon, keyed by **port number**, not folder. This is deliberate: tier 2's `devports.json` keys by full absolute path specifically to avoid folder-basename collisions (§3 above), so the client-facing route can't safely key on basename either — using the already-resolved port instead sidesteps the ambiguity entirely. By the time the UI navigates, it already has the resolved port (either from the "Dev servers" dropdown list, itself sourced from each session's `devServerPort`, or from a Recent-history entry). The daemon validates the requested `:port` against the **live set of currently-resolved ports** (the same values populated into `SessionSummary.devServerPort` for known folders) before forwarding — rejecting any port not currently resolved for a known folder with 403 `FORBIDDEN`. This is what keeps the proxy allowlist-only rather than "any port the phone asks for," per T13 below. Every entry point that can navigate here — the dropdown and a tapped transcript link (§5) — goes through this same check; there is exactly one trust boundary, not two.

The daemon reverse-proxies to `http://127.0.0.1:<resolved-port>/*` — **the proxy target host is hardcoded to loopback; only the port varies.** It never proxies to a non-loopback host.

**Known limitation, explicitly out of scope:** WebSocket/HMR proxying (e.g. Vite's live-reload socket) is not implemented. The pane is best-effort viewing — load, click around, check something rendered — not full dev-server parity. Framework asset paths that assume being served at `/` (rather than a proxied subpath) may have broken relative asset loading; no per-framework `base`/`basePath` rewriting is attempted. Separately (see "Iframe sandboxing" below): any dev-server app that loads its own assets or calls its own API via script-initiated `fetch()`/XHR, rather than plain `<script src>`/`<img>`/navigation, will find those calls blocked too, as a side effect of the opaque-origin sandbox — not a bug, but a likely source of "why doesn't my app load" confusion worth knowing about going in.

### Local file viewing (dev server's counterpart content source)

`GET /api/webpane/localfile?path=<url-encoded-absolute-path>` — reads a file directly off local disk and returns its bytes with a Content-Type guessed from its extension: `.html`/`.htm` → `text/html`; `.md`/`.markdown` → `text/markdown`; `.txt` → `text/plain`; `.png`/`.jpg`/`.jpeg`/`.gif`/`.svg`/`.webp` → the matching `image/*`; `.pdf` → `application/pdf`; anything else → `application/octet-stream` (the browser offers it as a download rather than rendering inline — no universal previewer is built for arbitrary formats). **No folder restriction** — any path readable by the daemon process is servable; this is an explicit, deliberate deviation, recorded in §9, with its risk and mitigations in **T15/T16** below. Used by Feature 4 (§5) for local links in transcript output (the stated use case: mockup files, spec files).

### Iframe auth (scoped cookie, path-limited) — shared by both content sources

An `<iframe src="...">` cannot attach a custom `Authorization` header — and critically, neither can any *subresource* request the loaded page's own HTML/JS issues afterward (its scripts, styles, images, and in-page `fetch`/XHR calls). This applies identically to both content sources above. A per-request URL token was considered and rejected: it would authenticate only the initial navigation, not the page's own follow-on requests, which don't inherit the referring URL's query string. Fix, shared by both:

1. **`POST /api/webpane-token`** — bearer-authed exactly like every other route (the PWA calls this immediately before setting the iframe `src`, via a real `fetch()` carrying a real `Authorization` header), body `{ kind: 'devserver', port } | { kind: 'localfile', path }`. `devserver` re-validates `port` against the live resolved-port set; `localfile` re-validates the path is actually readable — either way, failing fast with a clear error rather than deferring to first navigation. The response sets a cookie: `Set-Cookie: mv_webpane=<opaque-value>; Path=/api/webpane/; HttpOnly; Secure; SameSite=Strict; Max-Age=300` (5 minutes) — a random opaque value, bound to exactly the one resource (that port, or that path) it was minted for, held in the same in-memory map as every other daemon-side ownership/session record (cleared on restart).
2. Because the cookie's `Path` is `/api/webpane/`, the browser attaches it automatically to **every** request under that path — covering both content routes and all of their subresource requests — with zero cooperation needed from the loaded page's own code. This is the specific mechanic a header or a URL token can't provide, and it's why a cookie is used for this one route family despite the rest of the API being header-only.
3. `SameSite=Strict` means the cookie is **never** sent on a cross-site request — closing the CSRF vector for this route by construction, independent of and in addition to the existing Origin-allowlist check. `HttpOnly` keeps it unreadable from JS. `Path` scoping means the cookie is never sent to, and grants no access to, any other route — every other endpoint keeps header-only bearer auth unchanged.
4. The daemon's global bearer-auth hook gets one narrow exception, scoped only to `/api/webpane/devserver/*` and `/api/webpane/localfile` (not `/api/webpane-token` itself, which always requires the real header): a missing `Authorization` header falls back to validating the `mv_webpane` cookie against the in-memory store (must match the requested resource — the specific port, or the specific path — exactly, and not be expired) before rejecting with 401.
5. The PWA re-mints whenever the pane is opened or the user switches to a different dev server or file, rebinding the cookie to the newly selected resource. A stale **Recent** entry (§ below) whose port no longer resolves, or whose file no longer exists/is unreadable, fails validation on navigation and falls back to the pane's empty state.

This is a deliberate, narrow exception to T4's "header, not a cookie" rule — see **T14** below.

**Route-naming note:** the mint endpoint lives at a fully separate top-level path (`/api/webpane-token`, not nested under `/api/webpane/`) specifically so it can never collide with a proxied dev server's own routes — a dev server that happened to expose a path matching the mint route would otherwise be shadowed by it (routers, including Fastify's, resolve static routes before wildcards).

### Iframe sandboxing (same-origin script isolation)

Both content sources above are fetched through the daemon's own origin, which means any script inside that content would, by default browser same-origin rules, run with full same-origin access to the daemon's own origin — its `localStorage`, its cookies, and the ability to make credentialed `fetch()` calls to the **entire rest of the API** (`/api/sessions/:id/prompt`, `/api/sessions/:id/takeover`, etc.), not just the Web-pane routes. That would mean a dev server's own JS, or — more seriously, given Local file viewing above has no folder restriction — a local file's embedded script from *anywhere* on the laptop, could silently hijack the whole session: read the bearer token, inject prompts, take over sessions. A full same-origin XSS pivot into MicroViber's own control-plane API.

**Mitigation:** the iframe is rendered with `sandbox="allow-scripts allow-forms"` and **no** `allow-same-origin`. Per the HTML spec, this forces the framed document into a unique, opaque origin regardless of the URL it was actually loaded from — script can still run (needed for dev-server apps and interactive mockups to function) but cannot read the parent's `localStorage`, cannot access the `mv_webpane` cookie via script (the network-level cookie attachment needed to load the document in the first place is unaffected — only script-level access afterward is blocked), and any `fetch()` it issues is treated as cross-origin from an opaque origin — which the daemon's existing Origin-allowlist hook already rejects outright (`null` is never an allowed origin). This closes the same-origin pivot for both content sources without needing a second port, subdomain, or TLS certificate. See **T15** below.

### UI — address bar with dropdown

A single persistent address bar (not a separate folder-list screen) in the Web pane:

- **Collapsed:** shows the current full URL (`localhost:<port><path>`, or a local file's display name when that's the active content source), with the path portion visibly editable (dashed underline, blinking text cursor when focused) for the dev-server case — the host (`localhost:<port>`) is fixed to the resolved port of the currently-selected dev server and is not editable; only the path after it is. Typing/pasting a different host or port is rejected client-side (there's nothing to navigate to outside the resolved-port allowlist regardless — see T13 below).
- **Dropdown** (opened via the caret button, same style as the session-picker caret — see §4): shows, top to bottom:
  1. **Recent** — a client-side (per-device, `localStorage`) history of full URLs and local file paths actually visited through this pane, most-recent-first, capped at a reasonable count (10). Tapping a Recent entry navigates to that exact target.
  2. A divider.
  3. **Dev servers** — one row per folder with a currently-resolved port, in the format `<folder name>` / `localhost:<port>` (e.g. "studio" / "localhost:9005"), sourced from the same `/api/sessions` payload the picker already polls (each `SessionSummary` gains an optional `devServerPort: number | null` field, deduped by folder client-side). Tapping a row navigates to that port's root (`localhost:<port>/`) and becomes the new default.
- **Default on reopen:** whichever server/URL/file was last selected is remembered (client-side) and shown collapsed the next time the Web pane opens — there is no separate "pick a folder first" screen.

## 4. Feature 3 — UX/UI polish

### Title bar

A new, dedicated slim bar at the very top of the app shell (inside `Shell`, above everything else — visible on every screen: pairing, empty state, session view, session picker open, Web pane): app icon (small, ~20px, the same mark as the PWA icon) + "MICROVIBER" wordmark, left-aligned; the install button (§2) right-aligned when applicable. This is a deliberate departure from the original "fold the icon into the existing session header" idea — user preference, confirmed against a side-by-side mockup comparison.

### Session picker — dropdown, not a bottom sheet

The session-context header (unchanged: current session title + a caret button) now opens a **top-anchored dropdown panel directly below the header** — not the original bottom sheet. This reuses the exact same caret button style and expand-downward interaction as the dev-server address bar dropdown (§3), so the whole app has one consistent "chevron → panel appears directly below" metaphor instead of two different ones (an inline dropdown in one place, a bottom sheet in another).

- **Default content: Recent** — a flat, cross-folder list of the 5 most-recently-active sessions (or fewer, if fewer exist), sorted newest-user-prompt-first (unchanged sort key and behavior from the shipped `SessionPicker`). Each row shows the folder name inline (as today), so multiple sessions across different folders — the common case when working in parallel — are all one tap away without any folder navigation.
- **Secondary: "Browse by folder ›"** — a link in the panel's top row. Tapping it swaps the panel's content (in place, same panel, not a new sheet) to a folder-grouped list: one row per folder, showing session count and an aggregated state dot (amber if any session in it is `working`, else emerald if any `idle`, else grey). Tapping a folder swaps the panel content again to that folder's sessions (reusing the existing per-session row rendering), with a "‹ Projects" back row; a "‹ Recent" back row returns from the folder list to Recent.
- If there is only one distinct folder across all sessions, the folder-grouping level is skipped entirely (no "Browse by folder" link shown) — sessions for that single folder would just be a redundant echo of Recent.
- A scrim dims the content behind the panel (transcript/Web pane), matching the existing overlay pattern; tapping the scrim closes the panel.

**Tradeoff, noted deliberately:** bottom sheets are generally preferred on mobile for long lists (thumb reach). This design works because Recent is capped short and folder/session sub-lists are short too. If either list grows long in practice, revisit toward a bottom sheet.

### Composer action row alignment

In every composer state that shows action buttons (just-taken-over, queued, failed, etc.), actions are right-aligned with the primary CTA (**Send** normally, **Resend** in the failed state) as the rightmost element; **Hand back** (secondary) sits immediately to its left. Any status label (e.g. a "failed" pill) stays left-aligned within the same row, pushed apart from the action group by `margin-left: auto` on Hand back.

## 5. Feature 4 — Link handling in agent output

Added during this spec's own review cycle, not one of the three original Track B stories — but small in surface area since it entirely reuses the Web pane (§3) rather than introducing a new content-rendering mechanism.

### Classification

Every link the transcript's markdown renderer produces (already-shipped behavior — `functional-spec.md` §3 lists link rendering as part of its existing full markdown support) is classified at render time:

- **Local** — the link's target is a `file://` URI, a bare filesystem path (absolute or relative, no scheme), or an `http://` / `https://` address whose host is `localhost` or `127.0.0.1` (scheme doesn't matter — dev servers are almost always plain `http` locally, but an `https://localhost:<port>` link classifies as local too).
- **External** — anything else: an `http://` or `https://` URL to any other host (e.g. a GitHub PR link).

### Local links → the Web pane

Tapping a local link switches to the Web pane (§3) and loads the link's target there, through whichever of the two content sources applies:

- A `localhost:<port>` (or `127.0.0.1:<port>`) link goes through the **same port-allowlist check** as tapping a "Dev servers" dropdown row (T13), same trust boundary — a port not currently resolved for any known folder is refused and falls back to the pane's empty state, even though the tap originated from a transcript link rather than the dropdown. Unlike the dropdown row (which always lands on the port's root), the link's own path is preserved and navigated to directly — e.g. a link to `http://localhost:9005/scenarios/42` opens exactly that path, not the dev server's home page.
- Any other local path (a bare filesystem path, or `file://`) goes through **Local file viewing** (§3) — no folder restriction, per the explicit decision in §9 and threat rows T15/T16. A relative path (no leading `/`, no `file://` scheme) resolves against the `cwd` of the session whose transcript the link appeared in (already known — it's `SessionSummary.cwd`) before being sent to `/api/webpane/localfile`; an absolute path or a `file://` URI is used as-is.

### External links → the phone's own browser

Renders as a standard `<a href="..." target="_blank" rel="noopener noreferrer">`. The OS/browser opens it in a new tab outside the PWA, same as any normal web page — no custom interception needed; this is default `target="_blank"` behavior.

## 6. Feature 5 — `AskUserQuestion` support

Added during this spec's review cycle, prompted by a real observed failure: an `AskUserQuestion` tool call renders as a generic collapsed tool call today (functional-spec §3's default tool-call treatment), with no way to see the question or answer it from the phone — and the session can't even be taken over to fix that, for reasons below. **This is the one Track B feature that changes Track A's shipped behavior**, not purely additive.

### The actual bug (not just missing UI)

`domain/session-state.ts`'s `deriveState` treats *any* open turn (`turnOpen: true` from `transcript-meta.ts` — set whenever the newest assistant entry didn't stop with `end_turn`, which includes stopping on a tool call) as `working` for up to `OPEN_TURN_MAX_MS` (60 minutes) after the transcript last grew. An `AskUserQuestion` tool call is exactly this case: the assistant entry stops with `stop_reason: 'tool_use'`, not `'end_turn'`. Takeover is gated on `idle` (`assertIdleForTakeover` in `domain/ownership.ts`). Net effect, verified against the actual code (not assumed): **a session blocked on `AskUserQuestion` for less than an hour cannot be taken over at all** — the exact "pick up your phone within a few minutes" case the product exists for.

### Detection

Extend `lib/claude-adapter/transcript-meta.ts`'s scan to recognize, in the newest assistant entry, a `tool_use` content block whose `name` is `"AskUserQuestion"` (input shape: `{ questions: [{ question, header, options: [{ label, description }], multiSelect }] }` — the tool's own stable schema) and to check whether a later `user`-role entry contains a `tool_result` content block whose `tool_use_id` matches it:

- No matching `tool_result` yet → **pending**. Parse `input.questions` through a defensive zod schema at this boundary (Claude Code writes it, not the user, but every parse boundary in this codebase is validated regardless — architecture-spec.md §6, engineering standards).
- A matching `tool_result` exists → **resolved**; extract the answer for display, no longer actionable.

New `TranscriptMeta` field: `pendingQuestion: { toolUseId: string; questions: AskUserQuestionInput[] } | null`.

**Needs empirical verification before implementation**, in the same spirit as architecture-spec.md §2's F-numbered verified claims: the tool's name and input schema are known with high confidence (a stable, documented Claude Code tool schema), but *submitting* an answer back into a `--resume`'d, daemon-owned session — specifically, whether a `tool_result` content block can be written via the same stdin stream-json transport already verified for plain user turns (F11) — has not been empirically confirmed the way F11–F15 were for the takeover write path itself. Treat this as a prerequisite investigation task, not an assumption to build on directly.

### Session state: new `awaiting-input` state

`SessionState` (currently `'working' | 'idle' | 'stale'`) gains a fourth value: `'awaiting-input'`. `deriveState` gets one new evaluation rule, inserted right after the existing `!alive → stale` check and before every timing-based rule (`notify_idle`, the 20s/60min growth windows) — a structural signal, not a heuristic, so it overrides all of them: if the transcript scan reports a `pendingQuestion`, the state is `awaiting-input`, full stop, regardless of how recently the transcript grew. This is the actual fix — the session no longer masquerades as `working` while genuinely blocked on a human answer.

`assertIdleForTakeover` is extended to accept `awaiting-input` alongside `idle` for the takeover gate specifically — display stays distinct (below), only the gate treats them alike.

`functional-spec.md`'s composer-gating table (§3, "Composer gating on idle" — "working / idle / stale") needs a fourth row for this state once the story ships — noted here as a required reconciliation, per this workspace's standard practice.

### UI

- **Session list**: an `awaiting-input` session gets a distinct state-dot treatment from plain `idle` (exact visual TBD at implementation, but must be visibly different from both `working` and `idle` — it means "you're being waited on," which is more urgent than plain idle). It should also trigger the existing idle-push-notification mechanism (functional-spec §4) — a pending question is exactly the "you can now take over" signal that notification already exists to carry, arguably more urgently than a plain idle session — though see §7's note: that mechanism isn't yet wired into the shipped app end-to-end, so this may mean standing up its dispatch path for the first time, not just adding one condition to an already-firing pipeline.
- **Transcript rendering**: an `AskUserQuestion` tool call always renders expanded — never the generic "collapse to one line" treatment — showing the question text(s), header, and options as a real list. A **resolved** question renders the same layout read-only/dimmed, with the actually-selected option(s) highlighted, as transcript context.
- **Composer, per the confirmed decision**: no shortcut. `awaiting-input` shows the existing "Take over — send from phone" button exactly like plain `idle` does (the composer's status-bar state table gains `awaiting-input` as a second state mapping to that same button) — the question's options only become tappable once actually taken over, at which point tapping one submits the answer (mechanism per the investigation above) and follows the same accepted/queued/failed lifecycle as an ordinary sent prompt.

### Out of scope for this feature

- A free-text "Other" answer (already part of the tool's own schema) is rendered with the same generic text-input affordance already planned for structured options — no new input mechanism.
- Answering from a *stale* session (process exited) — same limitation as regular takeover.

## 7. Architecture & Spec Alignment

- **`microviber/docs/architecture-spec.md` §3 (component architecture / adapter quarantine)** — the adapter quarantine boundary itself is unaffected. The new port-resolution, proxy, and local-file-serving logic are new daemon-side concerns, not Claude Code internals, so they live outside `lib/claude-adapter/` — in a new `daemon/src/lib/webpane/` module (mirroring the existing `lib/` isolation pattern without needing the `~/.claude`-path FENCE 2 rule, which doesn't apply here). `api/app.ts` gains one new route family. `domain/` and `services/` are untouched **except for Feature 5** — see the dedicated bullet below, which is not a minor exception.
- **§4 (event model / API surface)** — `SessionSummary` gains one new optional field, `devServerPort: number | null`, populated by the new resolver. Three new routes follow the existing conventions (zod-validated params, the same error envelope): `POST /api/webpane-token` (standard bearer auth, no exceptions), `/api/webpane/devserver/:port/*`, and `/api/webpane/localfile` (the latter two — standard bearer auth **or** the scoped cookie, per §3's "Iframe auth" carve-out).
- **§5 (threat model T1–T12)** — extended with four new rows:

  | # | Threat | Mitigation |
  |---|---|---|
  | **T13** | The dev-server proxy is steered toward an unintended local service (a resolved port isn't actually a dev server) | Proxy target host is hardcoded to loopback only, never configurable; the resolved port is always visible in the UI (the address bar shows exactly what it's connected to). Accepted residual risk: tiers 1 and 3 of port resolution read content from the project folder itself, so a project's own files can influence the resolved port — accepted for a single-user personal tool where the "attacker" is limited to content already present in a folder the developer themselves opened in Claude Code. Tier 3 is kept to static/non-executing text scanning specifically so it cannot also become a code-execution surface. |
  | **T14** | The Web pane's scoped cookie (§3, "Iframe auth") reopens the CSRF surface that T4's "header, not a cookie" mitigation was written to prevent | Three independent bounds keep this narrow: (a) `SameSite=Strict` — the cookie is never sent on any cross-site request, regardless of request type (navigation, image, script, iframe), which is the actual CSRF vector; a malicious site cannot trigger an authenticated request to this route at all. (b) `Path=/api/webpane/` — the cookie is never sent to, and grants no access to, any other route; `/api/sessions`, prompt-sending, and takeover/handback all keep header-only bearer auth, completely unaffected. (c) The cookie's own capability is limited to viewing one already-selected resource (a port or a file) for 5 minutes — it cannot inject a prompt or take over a session even if somehow misused. Blast radius: strictly narrower than T4's original concern, which was about the main bearer token being CSRF-reachable for the *full* API surface. |
  | **T15** | Content served through the Web pane (a proxied dev server, or — especially — a local file with no path restriction) contains script that, absent isolation, would run with full same-origin access to MicroViber's own control-plane API: read the bearer token, inject prompts, take over sessions | Iframe sandboxing (§3, "Iframe sandboxing") — `sandbox="allow-scripts allow-forms"` with **no** `allow-same-origin` forces the framed content into a unique opaque origin. Script still runs (needed for the content to function) but cannot reach the parent's `localStorage` or cookies, and any `fetch()` it issues is cross-origin from an origin (`null`) the existing Origin-allowlist hook already rejects. This is what makes T16's accepted risk (unrestricted local file paths) tolerable — a malicious file's script is contained, not merely hoped to be benign. |
  | **T16** | A local link in transcript output, once tapped, causes a live read of *any* file the daemon process can read on the laptop — Local file viewing (§3) has no folder restriction, an explicit user decision | Accepted residual risk, by explicit choice, made after the tradeoff was stated plainly (this is a live read, not just a display of content already shown in the transcript — unlike T11's general "only displays transcript content" boundary). Bounded by: a tap is always user-initiated (no link ever opens automatically); T15's sandboxing contains whatever script the served file might contain; the cookie is single-resource-scoped and expires in 5 minutes; the daemon only ever serves raw bytes and never executes file content server-side. Unlike T13's port-allowlist (bounded to already-known project folders), there is no path boundary here at all — that is the explicit tradeoff being accepted. |

- **§6 (engineering standards)** — `microviber/devports.json` is read once at startup style, alongside `config.ts`'s existing zod-parse-at-startup pattern (though as a separate file, not an env var, since it's a structured map rather than a scalar). The new routes and resolver are covered by the same `npm run typecheck && npm run lint && npm test` gate.
- **Feature 5 — the Track A touch, and it's larger than it first looks.** `domain/session-state.ts` (`SessionState`, `deriveState`), `domain/ownership.ts` (`assertIdleForTakeover`), and `lib/claude-adapter/transcript-meta.ts` (`scanTranscriptMeta`, `TranscriptMeta`) are shipped Track A modules this feature genuinely modifies. So is a fourth, easy to miss because it doesn't consume `SessionState` directly: **`domain/notify-policy.ts`**. `NotifyPolicy` declares its own independent 3-value `State` type (`'working' | 'idle' | 'stale'`, not imported from `session-state.ts`) and gates every notify/dismiss transition on a literal `=== 'idle'` / `!== 'idle'` comparison. Growing `SessionState` to four values does **not** automatically make `awaiting-input` trigger a notification — §6's "should also trigger the existing idle-push-notification mechanism" requirement is not satisfied until `notify-policy.ts`'s own `State` type and comparisons are updated to treat `awaiting-input` as a notify-triggering condition too. Separately, and worth the story's planner knowing going in: `NotifyPolicy` currently has no call sites outside its own unit test — it is not wired into `app.ts`/`services/services.ts` in the shipped build — so §6's phrasing ("the existing... mechanism") describes code that exists but isn't yet live end-to-end; whether completing that wiring is in this story's scope or a pre-existing gap to file separately is a planning decision, not a design one, but it needs to be made explicitly rather than assumed. None of this touches the adapter quarantine boundary itself (transcript parsing already lives inside `lib/claude-adapter/`, where it belongs) or introduces a new write mechanism beyond what's flagged as needing verification in §6. No new T1–T12/T13–T16 threat row is needed: answer submission reuses the exact same takeover-gated write path (and its existing protections) as an ordinary prompt — it's "another kind of write," not a new trust boundary.
- **`microviber/docs/functional-spec.md`** — §3's composer-gating table ("working / idle / stale") needs a fourth row for `awaiting-input` (Feature 5, §6) — a genuine semantic change, not just documentation drift, since the state didn't exist in Track A. §3's session-list description also gets superseded by this spec's §4 (the dropdown-panel behavior), as already noted above.

## 8. UI/UX Guidelines Alignment

(`microviber/docs/functional-spec.md` §3 serves as the UI/UX guidelines reference for MicroViber — its registry `UIUX_SPEC` entry is `none`.)

- **Minimalism ("as few buttons and controls as possible")** — the title bar is a deliberate, acknowledged addition of one more persistent element beyond the three named in functional-spec §3 (session picker, composer, pane switch). It was chosen over folding the icon into the existing header after a direct side-by-side comparison; the user's explicit preference overrides the minimalism default here. The dropdown-panel session picker, by contrast, *reduces* net new UI surface versus the original bottom-sheet + separate folder-list-screen design this spec's own earlier draft proposed.
- **"Matches the Claude Code VS Code extension's own rendering... deliberately"** — one deliberate, scoped exception: Feature 5's `AskUserQuestion` rendering doesn't match the extension's own terminal/IDE presentation of that tool, because the extension doesn't need to solve "let someone without keyboard access answer it" — the interactive option list is new UI, not present in the extension. Every other tool call keeps the existing "collapse to one line, expandable on tap" treatment, unaffected.
- **Phone-injected prompts stay visually distinct** — unaffected.
- **Deviation, explicit:** functional-spec §3 describes the session list as "A sheet... not a tab strip." This spec changes that interaction to a top-anchored dropdown panel (§4), which supersedes that sentence. Recorded here as the deliberate correction; `functional-spec.md` itself gets updated to match once this story ships (reconciliation, per the standard clean-as-you-touch practice for this workspace's specs).

## 10. Out of scope

- Any iOS-specific UI, detection, or install guidance (feature 1).
- WebSocket/HMR proxying and per-framework asset-path rewriting for the dev-server pane (feature 2).
- Runtime-verification port detection (listening-socket inspection) (feature 2).
- `framework` / `startCommand` fields in `devports.json` are captured but not used by any UI in this story (reserved for a future "start this dev server for me" affordance).
- A universal file previewer for local file viewing (feature 4/Local file viewing, §3) — unrecognized extensions fall back to a plain download, not an inline preview.
- A one-tap answer-triggers-takeover shortcut for `AskUserQuestion` (feature 5, §6) — the explicit take-over step stays required, per the decision above.
- Answering an `AskUserQuestion` on a *stale* session, and any answer type beyond structured options / the schema's own free-text "Other" fallback (feature 5, §6).
- Any change to the takeover/handback write path itself, the actual markdown/link-rendering implementation in `Transcript.tsx` (only its tap-routing behavior is new), or notification *delivery* mechanics (all Track A, unaffected except for the state-derivation change feature 5 requires — see §7).
